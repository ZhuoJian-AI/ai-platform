第一章　服装企业基本情况与业务痛点

1.1 星途服装企业概况

星途服装（Starclothing）是一家面向中高端市场的服装制造企业，覆盖产品开发与供应链两条主线，拥有完整的款式—面料—打样—大货—品控—排产—对账链路。企业已上线 PLM（产品生命周期）、SCM（供应链）、ERP（人财物）、MES（制造执行）、CRM（客户与销售）五大业务系统，但系统间数据各自为政，业务决策高度依赖人工跨系统巡查与 Excel 汇总。

主营品类：双面呢大衣 / 压胶冲锋衣 / 纯棉 T 恤 / 牛仔裤 / 风衣 / 衬衫 / 卫衣 / 摇粒绒开衫
真实款号示例：P-FW2026-001（双面呢大衣）、P-FW2026-002（压胶冲锋衣）、P-SS2026-010（纯棉 T 恤）
组织架构：开发部 / 设计部 / 品控部 / 供应链部 / 生产部 / 财务部 / 商品部（7 个归口部门）
业务系统：PLM · SCM · ERP · MES · CRM（5 套系统，跨表数据闭环）

1.2 业务现状与七类痛点

从产品开发到供应链结算，星途服装在日常经营中面临七个反复出现的痛点。它们共同的特征是：数据散落在多个系统、人工逐单巡查、时效差、易遗漏、缺乏风险预警与闭环。

第二章　七大场景的 AI 解决方案

七个场景都用同一种终端任务方式：业务用户用自己的归口账号登录终端，新建一个任务、选好模型（glm-5.2）、粘贴一段很简短的提示词（写明"要做什么 + 针对哪些对象 + 用哪项技能"）后点运行。智能体会自己判断该调用哪些业务系统、按什么顺序查，跨系统把数据凑齐，边算边输出结构化结果，最后还自动生成一份 .docx 报告可直接下发。用户提示词之所以能写得很短，是因为"输出格式、业务名词字典、智能体的人设与规则"这三层已由平台和模板预先配好，用户只补"本次目标"即可。

📖 名词速查（看不懂的术语先看这里）
归口部门：负责某项业务的部门。本指南里每个场景都由一个归口部门用自己的账号去跑。
BOM：物料清单，即一件产品要用的所有材料明细。
RAG：检索增强生成——让 AI 先在企业自己的知识库里检索相关内容、再据此作答，而不是凭空编。
本体：用 Markdown 写的业务"字典"，告诉 AI 每个业务名词是什么、有哪些字段和编码规则。
端点：业务系统提供的一个个查询接口（比如"查工单"就是一个端点）。
流式输出：AI 边算边把结果一段段吐出来，不用等全部算完才看到。
闭环 / 回写：把处理结果写回业务系统留痕，使整件事有始有终、可追溯。
作用域（scope）：某个资源的可见范围，按 组织→部门→团队→用户 逐级限定。
Token：大模型按字数计费的单位，约等于半个到一个词。
API Key：调用大模型接口用的密钥，相当于一把"钥匙"。
glm-5.2：本 POC 使用的大模型（智谱出品）；终端里可选 glm / smart / balanced 三个别名，最终都路由到它。
DLP 安全围栏：对进出大模型的内容做脱敏/拦截的安全规则。

第三章　AI 底座管理端配置

ai_infra 控制台顶部为五个一级菜单（子系统），左侧为当前子系统的功能页面；所有资源按组织架构隔离。本章按子系统逐页介绍每个功能页（参照平台帮助文档），并附星途服装组织（以 admin 登录）下的真实页面截图。登录后组织自动锁定为当前管理员被指派的那个组织（顶部以蓝色标签展示本组织名，无需手动切换），所有查询自动限定在本组织内。管理员（admin）可管理本组织的组织架构、API Key、安全规则、智能体、工具等资源，但不能管理管理员账号；不可删除自己、不可降级自己。

3.1 平台总览与四组件

平台是一站式 AI 基础设施，提供大模型路由、智能体编排、工具接入与应用监控四类能力，由四个子系统共享同一套后台控制台与基础设施（数据库 PostgreSQL + 缓存 Redis + 向量库 pgvector）。

子系统定位核心能力
组织管理权限地基组织→部门→团队三级层级、管理员与用户管理、速率/预算限额逐级收紧
模型路由器统一大模型中转API Key、模型提供商、DLP 安全围栏、模型路由与用量管控
智能体平台智能体编排工作空间、智能体配置、RAG 知识库、判官、长期记忆、测试广场
工具连接器业务系统接入数据接口、技能（功能工具）、本体
应用监控台三子系统统一看板调用量、Token、延迟、错误率、DLP、成功率

3.2 组织管理

组织管理是全平台的权限地基。先建"组织 → 部门 → 团队"三级层级，每一级都能设两道上限：①速率（每分钟最多调用多少次、每分钟最多用多少 Token）②预算（最多花多少美元 / 用多少 Token）。下级能用的模型、速率和预算上限只能在上级范围内再收紧、不能突破上级；组织创建时的网址标识（Slug）一经设定不可修改。

组织架构

三栏列表：组织 → 部门 → 团队。选中组织展示其下部门、选中部门展示团队；可创建/编辑/删除组织与部门、设为默认组织。星途服装下已建 7 个归口部门（开发/设计/品控/供应链/生产/财务/商品）。

管理组织内终端用户（组织成员），同组织内用户名唯一，可设角色（组织管理员/成员）与启用状态。新建用户设初始密码（≥8 位），首次登录强制改密；可重置密码、停用/启用。星途服装下 58 个用户，7 个归口业务用户即在此维护。

API Key 管理

3.4 智能体平台

基于流程编排：运行时按"加载配置 → 检索知识库(RAG) → 载入长期记忆 → 智能体与工具多步往返（大模型边想边调业务系统）→ 保存记忆 → 判官复核 → 写运行日志"的顺序执行，结果边算边流式输出。智能体、判官模板创建时都要选"绑定到哪个节点"（组织/部门/团队），绑定后不可改；RAG 在左栏选中节点后新建、归属该范围；工作空间随节点自动生成。

3.7 分部门管理的安全模型

星途服装所有资源（本体 / 数据接口 / 技能 / RAG / 工作区 / 记忆）都按部门级别重新拆分。每个场景的归口用户登录后只能看到本部门可见范围内的资源——既允许跨部门数据流转（在调用方部门下重新实现一份数据接口、按需开放端点），又确保每个部门对外暴露的数据接口都是显式授权过的。

场景归口可见本体可见数据接口可见技能可见 RAG
开发部PLM（开发部级）PLM 端点/plm-query—
设计部SCM（设计部级）SCM 端点/scm-query—
品控部PLM 副本（品控部可见）PLM 端点/plm-query缺陷知识库（品控部级）
财务部Cross（无领域本体）ERP+MES+CRM/crm /mes /erp-query—
🔒 为什么"分部门"是安全的
  • 最小可见面：业务用户只能看到本部门被显式授权的端点，跨部门敏感数据（如财务对商品部报价、品控缺陷库）默认不可见。
  • 显式授权流转：跨部门数据流转必须由管理员在调用方部门下"重新实现一份数据接口"并开放端点，留痕可审计，杜绝暗箱穿透。
  • API Key 分部门签发：每个部门独立的 Key + RPM/token 预算上限，单部门异常不影响其他部门。
  • DLP 围栏按部门生效：客户名单、供应商报价等敏感数据外发规则按部门范围配置，越权外发即阻断/告警。
