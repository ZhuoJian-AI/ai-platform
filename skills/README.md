# skills

这个目录放**和这套平台配套的 skill**——交给 AI 读的操作手册，不是平台代码。

每份 skill 一个子目录，**互相独立、不交叉引用**。谁写的谁维护，改动只动自己那个目录。

## 目录里有什么

| skill | 管什么 | 谁维护 | 交给谁读 |
|---|---|---|---|
| [`模块需求/`](模块需求/) | 把一个说不清的想法**问成一份能开工的需求文档**。四段：开场判断要做哪几样 → 逼问需求 → 讲清做成什么样 → 成型为文档。全程不出现技术词 | 灼见 | 业务负责人的 AI |

## 预留位置

| skill | 管什么 | 谁维护 | 现在在哪 |
|---|---|---|---|
| `aifabei-subsystem-builder/` | 拿着需求文档**做出来 · 部署 · 接入平台**。含现状盘点、平台接入最小协议、契约校验、ECS 接入纪律 | 同事 | **还没进这个仓库**，目前独立打包分发。进来时放这里，和上面那份并列 |

## 两份是怎么衔接的

```
业务方说不清的想法
      │
      ▼  【模块需求】
需求文档（谁用 · 哪些部门什么角色 · 要做哪几样 ·
          能做哪些动作 · 哪些 AI 能做 · 数据在哪 · 什么算做成了）
      │
      ▼  【aifabei-subsystem-builder】
做出来 · 部署 · 符合平台接入协议
      │
      ▼  【人工，第一版不自动化】
在主脑后台登记模块 + 配部门授权 + 绑 AI 工具
```

**分工不重叠**：前一份只管「想清楚」，一个技术词都不出现；后一份只管「做出来」，
技术选型由它承担。中间的交接物就是那份需求文档。

完整背景见 [`docs/企业AI落地框架-开发需求-v3.html`](../docs/企业AI落地框架-开发需求-v3.html)。

## 加一份新 skill 时

1. 建一个自己的子目录，别往已有的目录里塞东西
2. 在上面的表里加一行：管什么 / 谁维护 / 交给谁读
3. 如果它和已有的 skill 有交接关系，在「怎么衔接」那张图里补一笔
4. **不要抄别的 skill 的内容进来**——需要引用就写指针。抄成第二份必然漂移

## 两个载体的说明

`模块需求/` 下有 `SKILL.md`（Claude Code 用，按需加载 references）和 `AGENTS.md`（Codex 用，平铺全文）。

**`AGENTS.md` 由 `scripts/build_agents.py` 自动生成，不要手改**——改了下次生成就没了。
要改去改 `SKILL.md` 或对应的 reference，然后重跑：

```bash
cd skills/模块需求 && python scripts/build_agents.py
```

之所以要两份，是因为 Claude Code 支持 `SKILL.md + references/` 的按需加载，Codex 不支持——
在 Codex 里分文件写等于白写。维护单一主体、生成两个载体，不手工维护两份。
